# Session — 2026-11-01: the offline queue merges instead of overwriting

**The bug (found by an e2e scenario, then fixed):** co-writing (E3) merges edits live, but a script typed while offline went back to the server through the queue's plain upload — `content` only, no `yjs_state`. If a collaborator had written in the meantime, the upload replaced their words and left the stored text and stored state disagreeing, so the next device to open the script saw the loss. `e2e/editor-offline-merge.spec.ts` reproduced it first (a fresh device showed "Alpha was offline." but not " Bravo stayed online.").

**The fix.** `mergeServerIntoLocal` (`lib/scriptos/cowriting.ts`) restores the device's saved shared document, applies the server's as a remote edit and returns the merged text and state. The queue (`reconcileWithServer` in `lib/scriptos/storage.ts`) reads the server's `yjs_state` and `updated_at`, merges, and writes the merge only if `updated_at` has not moved (a compare-and-set; it re-reads and merges again up to three times). It never falls back to overwriting: if the server cannot be read, or keeps moving, the script stays queued and retries with the usual backoff. With nothing to merge with (a script created offline, a server row that never had a shared document, a device with no saved document) the old plain upload stands. The editor's own save (`writeMerged` in `lib/scriptos/sync.ts`) does the same read-merge-write, in a scratch copy so the document being typed into is never touched, so a writer who keeps typing after someone else's queue sync merges instead of overwriting.

**Verified:** unit tests — 5 for `mergeServerIntoLocal` (both sides survive, state spells the merged text, commutative and idempotent, same-paragraph edits, null cases) and 10 for the queue path (`storage.merge.test.ts`: merge not overwrite, compare-and-set, device brought in step, re-read after a concurrent write, three conflicts stays queued, read error / write error write nothing, a writer who went on is not overwritten, and the three plain-upload fallbacks). e2e: `editor-offline-merge.spec.ts` (tab closed offline, sync from `/today` through the island's "Sync now", a fresh device sees both edits, text equals state, and the other writer typing again afterwards keeps all three).

**What the e2e taught (and a caveat).** The first version of the queue scenario kept the collaborator's window open while the writer went "offline"; Playwright's offline switch does not close an already-open websocket, so the collaborator received the offline typing live and the result came out garbled (an edit landed inside a scene heading). The scenario now opens the collaborator only after the writer's tab is closed, which is the real shape of the bug (a closed tab, the queue syncing from `/today`), and it passes 3 of 3 with both edits and a final third edit surviving. The garbled case, a live window and an "offline" one that is really still connected, was not investigated further; it deserves its own look (BACKLOG 3.33). Separately, `e2e/editor-cowriting.spec.ts` flakes about 1 run in 6 on this container with app code identical to `main` (2 failures in 11 runs); a clean `main` worktree passed 15 of 15 earlier, so treat the flake as load-dependent and not caused by this PR.

**Left (BACKLOG 3.33):** the queue sync does not broadcast its merged update to open editors (they merge at their next save); chunking large updates for the Realtime size limit; a private channel with a `realtime.messages` policy.
