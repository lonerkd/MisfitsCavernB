# Session — 2026-11-08: Spotify's refusals are said out loud; a device with no id (from the review)

Two of the review's findings. **A refusal was silent:** play/pause, next, previous, seek and volume on another device ignored a `false` from `controlPlayback` (Spotify answers 403 to an account without Premium or a device with no session), so the button looked broken. `SpotifyProvider` now routes them through `driveRemote`, which toasts "Spotify would not do that on <device>. Controlling another device needs Spotify Premium and a device that is awake." and, as before, changes the shared state only when the device did it. **A device with no id:** Spotify may report a restricted device with `id: null`; a song chosen in the suite fell through to this browser's player and a second player started. `playUri` now says "<device> will not take a song from here. Use “Play here”…" and stops. Writing the test showed a related edge: the poll compared the remote device's id with this browser's `deviceId` and treated `null === null` as "this browser's own player", so music on an id-less device was not seen as elsewhere at all while the in-app player was not ready; it now counts as this browser only when both ids are real and equal. **Tests:** 2 more in `SpotifyContext.sync.test.tsx` (a refused pause is toasted and the state does not change; next is toasted once; an id-less device gets no fetch and a toast). **Not verified against real Spotify** (a non-Premium account, a restricted device).
