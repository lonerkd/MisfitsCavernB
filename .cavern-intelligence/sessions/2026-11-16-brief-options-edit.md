# Session — 2026-11-16: brief options and phase (BACKLOG 3.14)

**Built:** on `/admin/brief-questions` an admin can now rename an option, add one, remove one, and change a question's phase (a question moved to another phase goes to the end of it). The edit panel has an "Option label" field per option, an "Add option" button (a new option takes its id from its label, never one already taken; ids never change afterwards because answers point at them), a "Remove option" button (off when only two are left) and a Phase select. Removing an option asks first (`useConfirm`) and says how many projects chose it; a number question has no options to edit.

**How answers are stored, and the decision:** `project_brief.value` names an option by id (a single choice: the id as a string; a multiple choice: an array of ids), and the trigger only checks on write, so dropping an option from `options` would leave answers pointing at nothing. Decision: **clean up, in one transaction**, not refuse. `admin_remove_brief_option(key, option)` deletes a single-choice answer that chose it, takes the id out of a multiple-choice answer (deleting the row if it was the only one), removes the option, and writes an audit-log entry (`admin_remove_brief_option`: label and answers cleared). It refuses if another question's `ask_when` waits on that option, or if fewer than two would be left. An admin cannot read other projects' answers, so `admin_count_brief_answers(key, option)` does the counting, and the existing question-removal confirm uses it too (it used to count through `project_brief` directly, which an admin's RLS would have under-counted).

**The floor under it:** `internal.brief_question_guard()` (BEFORE UPDATE OF kind, options on `brief_questions`) refuses, whoever writes: a change of kind on a question that has answers, and an option dropped from `options` that an answer still names. So a plain admin update cannot orphan answers either. The kind has no editor at all (not asked for); the guard is the rule if one is added.
