# Session - 2026-11-22: schedule versions (competitor parity, gap 4; BACKLOG 4.10)

The stripboard had one live schedule. It now has **named versions**: Studio › Production › Schedule › Versions. The owner saves the board as it is (which scene is on which shoot day, and the day dates), lists versions, **compares** any version with the live board (scenes moved, added or gone, day dates changed) and **restores** one. A restore asks first, **saves the live board as an auto version before it writes anything** (and does not start if that save fails), then puts each scene back with the ordinary `studio.updateScene` and each date back with `studio.setShootDayDate`, so the existing guards and the film-graph sync run; a day that exists only live keeps its date and a scene written since stays where it is. The order inside a day is the scene number, so a scene's day is all the order there is to keep. With no version the board behaves exactly as before.

Migration `20261122000600_schedule_versions.sql` (**to be applied to production and staging by hand after merge**): table `schedule_versions` (`project_id`, `label` 1-80, `snapshot` jsonb object with `scenes` and `days` arrays, bounded at 2000 scenes, 400 days and 400 kB, `auto`, `created_by` default `auth.uid()`, `created_at`). RLS from birth: one SELECT policy (`can_shape_project` or `has_capability(…, 'schedule.write')`), INSERT for people who shape the project with `created_by = (select auth.uid())`, DELETE for the same, no UPDATE policy; an invoker guard trigger (`internal.schedule_versions_immutable`, no helpers called) refuses every UPDATE, even the service role's. Snapshot, types, `database-and-security.md`.
